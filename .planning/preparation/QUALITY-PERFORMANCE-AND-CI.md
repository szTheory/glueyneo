# Glueyneo quality performance and delivery plan

Status: recommended design, not implemented or benchmarked. Researched 2026-10-01. Audience: implementers, reviewers, release maintainers, and frontend integrators. Read this when turning the first milestone into measurable acceptance criteria. Decisions below are project recommendations unless explicitly attributed to a source.

## Measure distinct outcomes

Glueyneo should make a claim only as broad as its evidence. Keep hardware conformance, game compatibility, deterministic replay, host safety, performance, and ease of integration separate. A passing screenshot does not establish sound correctness; two emulators agreeing does not establish hardware truth; a fast attract screen does not establish demanding gameplay performance.

| Dimension | First useful measurement | Regression rule | Evidence limit |
|---|---|---|---|
| Hardware conformance | Named CPU, bus, video, sound, timer and interrupt assertions | Previously justified assertions keep passing; changed expectations need source and explanation | Record which board/revision and observation support each result |
| Compatibility | Versioned game/configuration/scenario inventory | No silent loss of an established scenario | Report unknown, boot, attract, gameplay, completion and hardware-compared separately |
| Determinism | Canonical state, raw video and integer audio hashes for fixed input/RTC/seed | Identical supported builds and hosts produce the declared identical outputs | Frontend resampling, shaders and presentation are separate contracts |
| Host safety | Sanitizer failures, minimized fuzz reproducers, bounded resource failures | No known unresolved memory-safety failure in release paths | Passing fuzzing is evidence of exercised paths, not proof of safety |
| Execution speed | Emulated seconds per host second; host CPU and wall time per frame/scenario | Compare like-for-like on controlled hosts | Disable throttling for throughput; disclose it for realtime results |
| Tail behavior | Frame-time histogram, worst frames, audio underruns, missed deadlines and consecutive misses | Defined scenario and host-specific budgets | Do not pool unlike games/machines into an impressive percentile |
| Memory | Peak resident memory, core-owned bytes, allocations, decoded assets, snapshot size | Explain and budget increases against functionality | Separate immutable cartridge data, decoded caches and instance state |
| Adoption | Clean checkout build, relocated package consumer, example host, first diagnostic run | Execute the documented happy path in automation | Build success alone is not install/link/runtime success |
| Delivery | PR feedback latency, runner-minutes, flakes, release success | Investigate worsening trends; keep mandatory checks meaningful | Queue delay, execution duration and billed resources are different metrics |
| Documentation | Compiled examples, matching option/API descriptions, internal links | Update behavior and documentation in one PR | Link checking cannot establish that prose is true |

At preparation time every implementation metric is **not measured**. Never initialize a dashboard with fictitious zero failures or 100% compatibility. The first milestone must produce the initial records from working code.

## Build an evidence ladder

1. **Small deterministic tests:** unsigned arithmetic boundaries, explicit byte decoding, address mirrors, bank limits, clipping, sprite limits, timers, reset and watchdog behavior. Assert behavior, not the current function decomposition.
2. **State and sequence properties:** running A then B equals running A+B under identical scheduled inputs; save/load continuation equals uninterrupted execution; independent instances do not affect each other; invalid state restoration leaves the running instance unchanged; an acknowledged older persistence generation does not clear newer writes.
3. **Differential chip tests:** run pinned, licensed instruction vectors and compare bus events, flags, exceptions and cycle accounting. Record shared ancestry of the test generator and chip implementation. A vector generated by MAME or ares is a differential oracle, not automatically a physical measurement.
4. **Original diagnostic programs:** exercise a narrow Neo Geo feature with a defined pass/fail mailbox, visible output and reproducible build. Confirm at least key timing assertions on actual hardware when available. A custom test loader must be labeled so it cannot be mistaken for BIOS boot compatibility.
5. **Integration and adapter seams:** media load → reset → timestamped input → raw video/audio → snapshot → persistence export → unload/reload. Include missing BIOS, invalid media, insufficient buffers, unsupported configuration, failed allocation and malformed state paths.
6. **Replay scenarios:** deterministic inputs plus named checkpoints for legal homebrew and privately held game images. Include gameplay, midframe effects, sound commands, banks, protection, resets and long-running behavior. Attract loops are a separate inexpensive tier.
7. **Hardware observations:** retain measurement method, board identity stripped of owner identifiers, firmware/media hashes where appropriate, capture method, clock assumptions and uncertainty. Match digital pre-output signals where possible; do not compare an analog photograph to a raw framebuffer hash.

An expectation must record origin: specification, physical observation, emulator-generated reference, or Glueyneo regression. Snapshot updates need a reason; an automated job must not regenerate expected outputs merely to turn red CI green.

Canonical replay hashes cover emulated state, not host delivery/acknowledgment counters, diagnostic timestamps or container checksums. Restoration may correctly advance a host-facing persistence generation while reproducing identical guest state and output. Verify both invariants separately; never require byte equality of unrelated bookkeeping to establish deterministic continuation.

## Corpus and compatibility records

Each public fixture needs an identifier, source URL, immutable source revision, separate code/data/asset licenses, redistribution basis, build recipe and toolchain version, output SHA-256, required BIOS status, feature tags, input script, oracle, and expected failure mode. Hashes prove identity, not permission to redistribute. A permissive build system does not license bundled game art, music or firmware.

Prefer original tiny Neo Geo diagnostics that require no proprietary firmware. A replacement BIOS is a candidate only after its own per-file license audit. The local Playstead evidence and Neo Geo candidates are in [PROJECT-DNA.md](PROJECT-DNA.md) and [NEOGEO-HARDWARE-AND-ECOSYSTEM.md](NEOGEO-HARDWARE-AND-ECOSYSTEM.md). Playstead's GBA assets are not a Neo Geo corpus.

Maintain a separate private corpus directory outside source control. Public fork CI must never receive commercial images, private save states, private traces containing code/data, signing credentials or access to a maintainer's ROM collection. A trusted local runner can emit a scrubbed compatibility summary; that does not authorize uploading screenshots, audio, memory dumps or ROM fragments. Cartridge ownership does not establish redistribution permission, and legal rights to dumps depend on circumstances and jurisdiction.

Define the denominator before claiming coverage: system MVS/AES, board and protection family, title, revision, clone, region, BIOS revision and operating mode. Neo Geo CD and unrelated Neo Geo Pocket systems have separate scope. Track tested configurations and an explicit untested count. A percentage must link the frozen inventory revision and the exact attainment threshold. Avoid announcing a single timeless number of Neo Geo games.

Start with a representative feature matrix, then expand per title. A scenario is reproducible only when it records build and dependency revisions, cartridge/BIOS identity, model, deterministic RTC, input sequence, reset type and checkpoints. Private scenario results keep corpus fingerprints local by default. Public summaries may use already-public cartridge identities or metadata explicitly authorized for publication; redact private hashes and paths as well as the bytes themselves.

## Fuzzing and hostile inputs

Use coverage-guided fuzzing for media manifests/container adapters, cartridge-region normalization, save-state decoders, persistence import and public API call sequences. Add decompression limits before adding archive support. Set maximum bytes, entries, decoded sizes, total memory and execution steps; reject integer overflow before allocation. Keep archive extraction and filesystem paths out of the core. See [C-CORE-ARCHITECTURE.md](C-CORE-ARCHITECTURE.md) for the detailed boundary contract.

Run short deterministic regression corpora in PR CI, bounded fuzz smoke for touched parsers, and longer campaigns after merge or on a schedule. Promote every real failure to a minimized regression with a seed and reproducer command. Retain the original failure if retries are used to diagnose flakes. Quarantine requires an owner, a reason, replacement coverage where necessary, and an expiry; never disguise a critical failing check with continue-on-error.

Begin with Clang AddressSanitizer plus UndefinedBehaviorSanitizer. Use other sanitizers only where their platform and dependency requirements are understood. Add ThreadSanitizer when actual shared concurrency exists. A memory sanitizer build with uninstrumented dependencies is not a complete uninitialized-memory check. Do not spend PR time running the same assertion under every tool with no distinct fault model.

## Performance protocol

Use an optimized production-equivalent build without sanitizer instrumentation. The benchmark driver owns host timing; the core owns emulated time. Use a monotonic clock, explicit warm-up, repeated trials, a recorded scenario length and observable output checks to prevent dead-code measurement. Separate cold media decode, reset, steady gameplay, snapshot save/load and frontend delivery costs. Keep measurement allocations and logging outside the timed region.

Begin with a small C scenario runner producing machine-readable records. Python standard-library tooling may aggregate and compare results as a developer tool. Google Benchmark demonstrates warm-up, repeated trials and randomized interleaving, but introducing its C++ dependency is unnecessary unless its features later justify it [Q-07]. Prefer fewer, interpretable scenarios to hundreds of microbenchmarks. Use microbenchmarks after a profile identifies a bottleneck.

Compare the PR and its exact baseline on the same machine and toolchain in interleaved trials. Store both revisions. Record CPU model/architecture, OS, compiler and options, build type, power mode, temperature/throttling context when obtainable, core affinity policy, dependency revisions, media/scenario hashes, output hash, sample count, warm-up and measurement duration. Do not publish serial numbers, hostnames, usernames or home paths.

First choose one Apple Silicon host class and one x86-64 host class. Add an efficient ARM/Linux device once there is a real target and available hardware. Hosted CI is useful for detecting severe changes and for trends; small timing changes there are advisory. Dedicated benchmarks must run only trusted revisions in an isolated environment, without public fork access or unrelated personal data.

Publish p50/p95/p99 and maximum frame work together with throughput, memory and deadline misses. A fixed output-equivalence requirement applies to optimizations. Faster output that drops sprites, alters sound, skips waitstates or lowers internal timing precision belongs to an explicitly different compatibility profile, not an undisclosed performance win.

### Extreme tails require appropriate experiments

For a deadline-miss probability p, zero failures in n independent trials has a one-sided 95% upper bound p = 1 - 0.05^(1/n). Setting p to 0.00001 requires at least **299,572** zero-failure trials. This is our calculation using the binomial model; NIST describes exact confidence limits [Q-08]. At an illustrative 60 frames/second that is about 83.2 minutes. This is not a claim about the exact Neo Geo refresh rate, nor a stable estimate of the p99.999 latency value.

Real frame times are correlated and affected by scene changes, thermal state and operating-system scheduling. Many repeated easy frames do not justify an independent-trial assumption. For rare-tail goals use multiple long sessions, demanding scenes, cold/warm starts and documented host conditions; preserve per-session results and correlated blocks when estimating uncertainty. A million frames can still leave sparse tail evidence. Do not turn p99.999 into a gate on a ten-second PR benchmark.

Avoid coordinated omission: an unthrottled core throughput run cannot reveal a frontend that stops sampling while stalled. Realtime tests must count expected presentation/audio deadlines as well as completed work. Record consecutive missed deadlines and buffer underruns, since clustering matters to players. Host-side dynamic audio resampling must not change the emulated clock to make benchmarks look better.

### Initial budgets are hypotheses

| Budget | Proposed starting policy | How it becomes a gate |
|---|---|---|
| Steady core allocations | Zero after configured media initialization for normal frame execution | Allocator counters in deterministic tests; snapshot buffers sized before use |
| Determinism | Zero unexplained canonical output mismatches on the supported comparison matrix | Exact expected identities and a verified oracle |
| Performance regression | Investigate a repeatable >5% scenario slowdown; no automatic tolerance inflation | Advisory until repeatability is characterized; then confidence plus practical effect size |
| Realtime headroom | Aim for p99 core work below half the emulated frame period on the named baseline host | Calibrate once real workloads exist; frontend cost remains separately measured |
| PR feedback | Aim for median execution under 5 minutes and p95 under 8 minutes | Measure after first workflow; track total runner-minutes too |
| First local build | Aim for under 60 seconds on a documented representative machine | Measure cold and warm builds, including dependency preparation separately |

These are proposed engineering targets, not observed values, guarantees, or reasons to weaken correctness. A documented accuracy fix can legitimately cost runtime. Such a change should include measurements and an explicit accepted budget revision rather than remain blocked forever by an arbitrary speed ratchet.

## CI lanes and efficient feedback

Start with one understandable workflow and a small supported matrix. CMake presets should drive both local and CI commands. Do not add a workflow engine around the workflow engine.

| Lane | Trigger | Initial contents |
|---|---|---|
| Fast required | Every PR and required merge candidate | Formatting of owned C; workflow lint; license/fixture-manifest checks; Linux Clang build and tests with ASan/UBSan; deterministic diagnostic; installed consumer |
| Portability required | Source/build/API changes | macOS arm64 and Windows MSVC build + integration smoke; lightweight GCC build; static/shared consumer coverage divided among jobs |
| Bounded fuzz | Parser/state changes, plus main | Minimized regression corpus and time-limited fuzz smoke; strict resource limits |
| Extended | Scheduled trusted main and release candidate | Long fuzz, broader CPU vectors, optimization/compiler determinism, long replay, archive/install relocation, additional architectures as supported |
| Performance | Same-host comparisons; scheduled trusted builds | Repeated benchmark scenarios and trend artifacts; only reproducible thresholds become required |
| Release | Qualified release commit and draft identity through explicit dependent jobs | Clean packaging, license/SBOM inventory, adapter load/consumer smoke, checksums, provenance and complete draft publication; no dependency on a tag that may not exist yet |

Use an always-started required aggregate check that knows which lanes apply. It must fail on failed or unexpectedly cancelled/missing dependencies, and permit a deliberate skip only when the classifier says the lane is irrelevant. Unknown changed paths select the conservative full set. GitHub documents that skipped whole workflows can leave required checks pending, and merge queues need the merge_group trigger [Q-03]. Test the classifier and aggregate behavior, including docs-only PRs and workflow changes, when implemented.

Run independent build jobs concurrently; within each job use available cores bounded by memory. CTest parallelism should account for multi-threaded child tests so N jobs do not each consume N cores. Shard only after timing reveals a long critical path. Avoid rebuilding identical binaries merely because tests have different labels. PR cancellation should cancel superseded runs for that PR; release publication must be serialized and must not be cancelled half way through.

Cache only when restore/save overhead is less than measured work avoided. Prefer compiler caches with OS, architecture, compiler identity, options and dependency revision in their scope; do not restore stale CMake build directories. Keep a cold-build check. ccache has explicit correctness caveats and statistics; inspect actual hit rate and time saved [Q-06]. Artifacts carry build outputs between jobs; dependency caches are not release artifacts [Q-05]. Never cache secrets, proprietary inputs or signing material.

Review CI cost after each milestone: slowest critical-path jobs, low-yield duplicates, setup/download time, cache churn, flaky tests, matrix gaps, artifact retention and cancellation. Remove a test only after documenting which independent failure signal is redundant or no longer valuable. Keep rare but severe boundary regressions. Do not use raw coverage percentage or test count as a quality proxy.

## PR merge and release automation

The user has authorized normal PR creation, qualifying merges and automated releases. Preserve branch protections and automate the checks rather than require recurring human approval. Configuration credentials or an unavailable signing account may be a concrete external blocker; green checks must not be invented to get around it.

Recommended policy:

1. Work on branches and use small PRs. Inspect relevant open issues/PRs at milestone start and before shipping; deduplicate known work. Use Conventional Commit squash titles so release intent is machine-readable.
2. Require trusted checks for the current revision and merge candidate, with no unresolved blocking review finding. For autonomous changes use a separate evidence-based review pass; adding an approval bot is not a substitute for review.
3. Enable native auto-merge or merge queue where supported. Re-evaluate after every push. Never merge because an earlier SHA was green or because a check with a matching name came from an unexpected source. Bind required checks to trusted producers/rulesets.
4. Maintain a release-please release PR using its simple/manifest strategy and one version source. CMake should derive its project version from that source. A pre-1.0 breaking API change gets a deliberate minor bump and migration note; version policy must be configured explicitly.
5. After the release PR qualifies and merges, build and smoke-test the exact intended release commit. Stage a draft release and all assets. Publish automatically only when the expected set, hashes and provenance are complete. Prefer immutable releases once this path is proven.
6. Treat retries as idempotent: same tag must refer to the same commit and expected asset hashes. Never silently replace published bytes. Fix a failed release with a corrected new version when publication is already immutable.

release-please supports version/changelog PRs and separate release controls [Q-01]. Qualify a pinned manifest configuration using release-type simple and draft enabled; the action's release-type-only shortcut does not provide advanced configuration. The current upstream schema says draft releases do not create a tag until publication [Q-14]. Build from the verified exact commit SHA in explicit dependent jobs and address the draft by release identity; a tag-triggered build could otherwise deadlock. Verify the pinned action's bundled version and returned metadata rather than assume current upstream options exist in it.

Add a reconciliation path that can find the expected existing draft and resume missing asset staging after interruption, without relying solely on a one-time release_created output. Test interrupted upload, repeated execution, wrong commit identity, conflicting assets and incomplete staging before calling publication unattended. GitHub recommends draft → attach assets → publish because immutable publication locks the tag and assets [Q-09]. Avoid the common sequence that publishes first and tries to attach binaries afterwards.

**Current token caveat:** GitHub now documents that some PR events created using GITHUB_TOKEN start approval-required runs, while most recursively triggered events remain suppressed. For unattended release PR checks use a narrowly scoped GitHub App installation token; a carefully scoped PAT is a fallback, not the default [Q-02, Q-04]. Do not repeat older blanket claims that all such PR runs simply never exist. Prefer explicit dependent jobs for asset publication instead of relying on an event that may be suppressed.

Untrusted PR jobs get no release credentials. Use read-only default permissions and elevate only the job that needs them. Pin actions to verified commit SHAs, update them deliberately, and pass untrusted titles/paths through structured arguments or quoted environment variables. Privileged workflow_run or pull_request_target jobs must not execute arbitrary PR code [Q-10]. Current GitHub docs also distinguish SHA pinning from advisory coverage; do not assume immutable pins alone provide vulnerability alerts. Keep a dependency/action update review process.

Attestations identify build provenance; they do not prove emulator correctness [Q-11]. Source archives must build without a Git checkout or network fetch. Record toolchain and dependency locks; normalize timestamps and build paths where supported. SOURCE_DATE_EPOCH helps reproducibility, but reproducibility must be demonstrated by comparing independent builds [Q-12]. Signing/notarization may add expected differences; compare unsigned payloads separately.

## Release experience and secrets

Ship a source archive and usable SDK/adapter artifacts as early as a truthful alpha capability exists. For macOS, first qualify a libretro core in a pinned RetroArch installation; see the architecture and hardware reports. If that becomes an integration bottleneck, a thin SDL3 harness can provide a downloadable test application. Do not build a launcher/library manager. Apple signing/notarization is a separate distribution concern whose credentials and account availability must be established; do not promise a warning-free app before that is working [Q-13].

The library should require no secrets. Local automation may use an ignored .env.local through an explicit launcher; the core never searches for or loads it. Commit only placeholder variable names in an example. Prefer GitHub configuration variables for nonsecret settings and Actions secrets for credentials. Use short-lived credentials where available. Avoid source-time shell execution of a downloaded or untrusted dotenv file. Never dump the environment into logs.

Public artifacts must exclude commercial media, private test outputs, personal paths, local machine names, account identifiers and private git author emails. Use repository-relative paths, reproducible path remapping and an established public commit identity. A release scanner must inspect archives and debug metadata, not merely tracked filenames. Ask for missing identity/account facts only when publication actually depends on them.

## Keep the quality loop useful

At each milestone close, publish what was shipped, supported configurations, failures/unknowns, conformance additions, performance deltas and CI cost. Pick the weakest high-impact dimension using actual evidence and address it in the next milestone. Keep one detailed current milestone, an outlined next milestone and a longer direction list. Do not schedule the whole hardware implementation in fine detail before feedback exists.

Automate verification when it is repeatable: real build/install/load seams, deterministic replays, persistence continuation, version checks and release artifacts. Human work should be limited to genuinely unavailable physical measurements or a decision that cannot be inferred. Record why a check still requires hardware/person input, and replace it with a fixture when possible. A blocked physical test narrows the claim; it should not automatically block unrelated releases.
