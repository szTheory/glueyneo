# Portable C core architecture and engineering contract

Status: research and proposed defaults, not an implemented design or initialized GSD plan. Researched **2026-10-01**. Scope: native embedding, C, scheduling, state, builds, testing, and optimization. Audience: core developers, frontend integrators, maintainers, security reviewers, and performance engineers. Source IDs resolve in the ledger below; recommendations are synthesis, not claims that a source endorses glueyneo.

## Recommended foundation

Build a C17 library with an opaque machine instance, deterministic host-driven execution, explicit memory ownership, and a thin libretro adapter. Keep presentation, device clocks, files, networking, secrets, and process management in hosts. Use CMake, CTest, and a small vendored C assertion framework. Establish scalar reference behavior and reliable serialization before pursuing architecture-specific acceleration.

The largest immediate uncertainty is dependency feasibility. Mature CPU/audio code accelerates delivery, but popular candidates contain mutable global state. A bounded integration spike must establish reentrancy, complete state capture, timing limitations, and license provenance before selecting them. Do not mistake a C API wrapper for instance isolation.

## Native API and host responsibilities

Expose a small header with `glueyneo_` symbols, an incomplete machine type, C++ linkage guards, and a documented calling convention/export macro. Keep private device structures out of installed headers. Use fixed-width fields for ABI-visible flags/statuses instead of compiler-sized enum fields; buffers use pointer plus length. Native pointers and `size_t` still follow the target ABI: this interface is not a cross-architecture wire format.

Use size-tagged configuration/result structures with documented defaults, rejected unknown mandatory flags, and a separate API/ABI version query. Read only fields present within `struct_size`; never copy a newer structure over an older caller's buffer. Add feature queries when needed, not a generic untyped command bus. Pre-1.0 releases may change the interface with release notes and matching adapter updates; no permanent ABI promise yet.

Operations should cover create/destroy, content load/unload, reset, bounded execution, input submission, media output, persistent-memory exchange, and serialization. Define lifecycle errors and output-buffer behavior. Return actionable codes for unsupported hardware, incompatible states, invalid content, capacity limits, and allocation failure. No `exit`, process signal changes, locale changes, environment reads, unsolicited printing, or callback unwinding across the C boundary. Internal assertions describe programmer invariants; untrusted bytes take checked error paths. Arbitrary invalid host pointers cannot be made safe by argument validation.

| Seam | Contract to design and demonstrate |
|---|---|
| Content | Validated normalized ROM/BIOS spans with explicit sizes and identities. A borrowed immutable load path requires bytes to remain alive until unload; provide a copying convenience path with reported memory cost. ZIP parsing, file selection, and format conversion belong in optional import/host code. |
| Allocation | Optional per-instance allocator plus user data; all allocations freed by the matching allocator. Specify alignment, failure, lifetime, and zero-size rules. Allocate variable storage at creation/load; target zero core allocations during steady execution. Caller buffers handle large outputs. |
| Execution | A bounded run operation reports actual emulated time advanced and why it stopped. A frame helper uses the same engine. No sleeping or reading wall time. Report actual timing capabilities if a backend can stop only at instruction boundaries. |
| Video | Document pixel word/byte interpretation, pitch, dimensions, visible rectangle, aspect metadata, and lifetime. Start with one unambiguous software format. Never force a graphics context or window. Video delivery does not mean host presentation completed. |
| Audio | Batch interleaved signed PCM with documented rate, channels, sample count, rounding, clipping, and buffer ownership. Backpressure cannot silently lose samples or change guest time. Core output timestamps and sample counts support deterministic capture. |
| Input | Host supplies logical buttons, coin/service/test controls, and device capabilities. State exactly when input is latched. Initially a documented boundary is sufficient; timestamped events require actual subframe support. Polling must not introduce host-time nondeterminism. |
| RTC/configuration | Host supplies initial RTC state and any deliberate elapsed-time adjustment. Subsequent progress derives from emulated time. Region, machine profile, BIOS, DIP switches, and seeds become reproducibility inputs. Avoid implicit local timezones. |
| Persistent media | Export bytes plus medium identity and monotonic dirty generation. Host acknowledges the generation only after its durability policy succeeds. An old acknowledgement cannot clear newer writes. Explicit snapshots eliminate polling file modification times. |
| Diagnostics | Structured status plus optional synchronous cold-path log callback with user data. Never require a logging framework or network endpoint. Document callback lifetime, reentrancy restrictions, and thread. |

Prefer media buffers/results to callbacks crossing an FFI per pixel or sample. If callbacks are used, deliver batches and prohibit reentering the same machine while it runs. Independent machine concurrency requires all mutable guest/backend state to belong to an instance; immutable lookup tables may be shared. Lazy initialization must also be audited.

Playstead currently launches an external emulator process; a native C seam does not already exist. Its adapter and save contracts are useful requirements: explicit capabilities, media compatibility fingerprints, bounded stop, and acknowledged persistence. Keep its existing save compatibility assumptions in view during a dedicated integration spike. See [PROJECT-DNA.md](PROJECT-DNA.md), DNA-01 and DNA-02. Do not put frontend process supervision into the core.

## Timing, device boundaries, and dependency gates

Organize around machine composition, scheduler, bus, CPU devices, video, sound, cartridge/protection, state, and public API. Keep dependencies directed: host adapters call the public API; machine orchestration connects devices; device code uses narrow bus/timing contracts. Use concrete structs/functions internally. Avoid a universal component framework, virtual bus objects per access, or premature plugin machinery.

Choose a 64-bit integer scheduler quantum fine enough for evidenced hardware phases; do not assume every event occurs on a whole master-clock boundary. Maintain exact clock ratios with integer remainders and report rational timing. Define overflow bounds and deterministic ordering for coincident events. Start with a small fixed event set and explicit minimum-deadline selection; a generic priority queue is unnecessary until measured requirements justify it. Hardware frequencies and phase evidence belong in the hardware report, not inferred from display refresh.

CPU reads/writes must preserve width, byte lanes, order, side effects, waits, interrupt acknowledgement, and bank changes. Synchronize sound commands, timers, raster changes, and bus-visible devices at the appropriate time. A memory inspection function must avoid read side effects; fetching for a debugger cannot acknowledge an interrupt. MAME's restartable CPU/memory contracts illustrate how complicated accesses spanning synchronization boundaries become. [C-16, C-17]

Compare instruction stepping with cycle stepping using the Chips author's explanation: cycle stepping exposes intermediate execution, while an instruction interpreter needs sufficiently precise internal callbacks to expose equivalent interactions. Neither simply counting instruction cycles nor calling every device once per frame proves accuracy. [C-13] Retain explicit known timing limitations until hardware tests resolve them.

At pinned Musashi revision `313ebf1bd9f4d0d93341eb5ce21fd8a119e9dbdd`, `m68kcpu.c` contains global CPU, cycle, exception, and jump-buffer state. Its context API is not proof of independent parallel instances. [C-14] At pinned Geolith revision `194024931935eff2092e36fc4f8e53e62ed11097`, YMFM-C contains static register/FM/SSG state and shim timer/output state. [C-28, C-29] Require an inventory of every mutable static/global, callback closure, initialization table, and serialized field before adoption. Contextization must preserve upstream behavior and retain a small, documented patch set.

Use the earliest spike to compare contextized C reuse against an upstream C++ chip implementation behind a C ABI. The latter needs an explicit scope decision if pure-C production remains a requirement. A serialized singleton backend is only a documented temporary limitation, never evidence for scalable multi-instance operation. A fresh CPU or FM implementation is a major research undertaking, not the automatic fallback.

For generated opcode tables, keep the specification/generator understandable, check generated output into release sources, and verify regeneration separately. Musashi demonstrates this approach's motivation through `m68kmake`. [C-15] Cross-compilation must not try to execute a target-architecture generator on the build machine. Test opcode semantics against independent evidence; generating implementation and expected outputs from one formula leaves common-mode errors.

## C rules, rendering, audio, and measured optimization

Require 8-bit bytes and exact-width integer types at compile time. Use unsigned arithmetic for guest modular operations and explicit sign extension. C integer promotions, signed overflow, shifts, aliasing, and object representation need deliberate handling: cast before widening shifts; bound shift counts; avoid shifting negative signed values; do not reinterpret unaligned byte buffers through integer pointers. Decode endian values explicitly or through safe copies; do not map hardware registers with C bitfields. Check lengths before pointer arithmetic and multiplication. These rules derive from C's specified semantics, not particular compiler behavior. [C-03]

Avoid VLAs, unbounded recursion, hidden allocation in helpers, packed runtime structs, GNU-only dispatch by default, and process-global mutable caches. Use `const`, meaningful units in names, short cohesive functions, and small `static inline` helpers where useful. Comments explain hardware evidence, timing assumptions, and surprising behavior; names explain routine mechanics. Keep generated/third-party code visibly distinct. Do not promise arbitrary microcontrollers: first support desktop 64-bit macOS/Linux/Windows, then validate 32-bit and constrained targets with explicit memory budgets.

Render scalar output first with correct sprite ordering, clipping, palette behavior, scaling, and raster updates. Decode/cache immutable graphics when memory measurements justify it. Keep mutable cache invalidation explicit and exclude derivable caches from portable snapshots. SIMD kernels must match scalar output on boundary/alignment cases; never ship a binary requiring the developer machine's instruction set accidentally. Keep GPU presentation and shaders in frontends initially.

Audio state includes chip timers, fractional phase, filtering, mixer history, and resampler delay. Prefer a proven, license-compatible resampler with deterministic arithmetic and documented coefficients over a hurried custom DSP design. A fixed canonical output configuration, provisionally 48 kHz stereo PCM, limits the first validation matrix; preserve internal hardware rates exactly. Decide final rate/filter through frequency-response, aliasing, latency, clipping, and cost measurements. Host synchronization to physical audio/video devices is separate; libretro documents dynamic rate control for their drifting clocks. [C-18]

Establish a release optimization baseline without `-ffast-math`/`-Ofast`; GCC documents that these relax semantics. [C-24] Evaluate `-O2`, `-O3`, LTO, and representative PGO using identical deterministic workloads. Prefer data layout, reduced redundant work, and bounded batches before assembly/JIT/threading. Record build flags, CPU, workload, output hashes, allocations, peak memory, throughput, and frame-time distribution. Extremely rare percentile estimates require enough independent observations; always include worst observed stalls and sample counts. Core throughput and frontend latency are separate measurements.

Optional event traces should use numeric records, emulated timestamps, bounded storage, and explicit drop counts. Format strings outside hot loops. A compile-time-disabled trace should leave no trace calls/storage, verified by build inspection and measurement; do not claim runtime-disabled instrumentation is free. Basic cold-path errors remain usable without tracing.

## State, replay, rewind, and trust boundaries

Serialize explicit fields/chunks with magic, format version, sizes, machine/content compatibility fingerprint, and integrity check. No native pointers, callback addresses, padding, host handles, or raw structs. Bound every length and allocation; reject unknown required chunks and inconsistent combinations. Validate into temporary state and commit atomically so a bad snapshot cannot half-mutate a running machine. Hashes detect identity/corruption, not provenance or safety.

Capture CPU partial execution if supported, scheduler deadlines/phases, pending interrupts, bus latches, video state, chip/audio history, and pending outputs. Rebuild derivable caches deterministically. Document whether snapshots require an execution boundary; do not expose arbitrary-cycle snapshots prematurely. Serialization must round-trip across supported builds/architectures before making that compatibility claim. SameBoy's public instance APIs and state organization are useful comparator material, not a format to copy wholesale. [C-12]

Separate canonical emulated-state identity from host delivery and persistence acknowledgment bookkeeping. A valid restore can advance a host generation while leaving the restored guest state identical; deterministic hashes must exclude host-only counters and diagnostics. Transient host execution machinery such as a jump buffer is recreated at a safe execution boundary, never serialized as guest state. Test restoration and initialization error paths as well as normal execution.

Battery saves are durable user data; emulator snapshots may remain version-bound. State the policy for each. On restore, host-facing persistence bookkeeping must remain monotonic and recompute dirty state: an old snapshot must not roll acknowledgement generations backwards. Speculative run-ahead cannot commit battery saves, external notifications, or authoritative media output. Frontends own rewind history/compression and netplay transport; core determinism/state APIs enable them. Stable serialization size and layout help libretro rewind, whose adapter-specific constraints must be checked against the canonical header. [C-10, C-11]

Treat ROM descriptors, archive imports, states, cheats, and debugger requests as separate hostile-input surfaces with size/time budgets. The core does not need filesystem privileges or a network. Host isolation remains useful because portable C plus sanitizers is not a memory-safety proof. Corpus manifests must carry origin, redistribution license, content hash, hardware profile, initial state/seed, inputs, and expected evidence. Never turn private commercial dumps, paths, or save contents into public fuzz artifacts automatically.

## Build and verification contracts

Propose CMake **3.24 minimum**, separately pinned current CI toolchains, Ninja for development, and ordinary Make/IDE generators for consumers. This floor is a design choice, not a latest-version claim. Use one library target with `glueyneo::glueyneo` alias and `BUILD_SHARED_LIBS` support. Keep options under `GLUEYNEO_`; disable tools/tests by default when embedded. Use target-scoped include paths, definitions, language requirements, warnings, and visibility; do not impose warnings-as-errors or optimization flags on consumers. [C-04]

Install headers and libraries through standard directories, export relocatable CMake configuration/version files, and supply a pkg-config file including any private static-link dependencies. Set shared-library ABI identity deliberately. Keep build and install include interfaces separate. [C-05] Commit portable `CMakePresets.json` configurations; ignore machine-specific `CMakeUserPresets.json`. [C-06] Avoid universal-build, sanitizer, LTO, and package-mode Cartesian products: choose representative supported combinations.

The core source archive must build offline from a clean directory without Git history, Python, network downloads, SDL, or a C++ compiler unless an explicitly selected backend changes that contract. Vendored dependencies need pins, licenses, checksums, update notes, and local patches; tests can vendor Unity's small C sources. Optional hosts can find system packages. `FETCHCONTENT_FULLY_DISCONNECTED` is not a reliable first-configure network prohibition; CMake explicitly requires prepopulated/local content. [C-07]

CTest is the single test entry point. Unity provides small portable C assertions; use explicit runners initially, without requiring Ruby/Ceedling. [C-08, C-09] Property loops use reproducible seeds and dump minimal replayable failures. Adopt a shrinker only where it reduces real triage effort.

| Evidence family | High-value checks and failure cases |
|---|---|
| API/lifecycle | Create/destroy repeatedly; reset/load failures; allocator failure at each allocation; callback lifetime; invalid ordering; undersized output; independent interleaved instances. |
| CPU/bus | Legal and illegal opcodes, flags, boundary arithmetic, interrupts, exception paths, unaligned accesses, endian lanes, bank switching, side-effecting reads. Use independently licensed vectors. |
| Metamorphic | Save→run→restore→same input yields identical output/state; run(N+M) equals split execution at supported boundaries; batching preserves audio counts; scalar and accelerated paths agree; reset is reproducible for a fixed profile/seed. |
| Differential | Compare selected traces against independent implementations and hardware evidence. Normalize intentionally undefined state; do not promote a popular emulator's output to unquestionable truth. |
| Fuzz | Separate loader/state/cheat targets; bounded execution sequences; malformed sizes and compressed expansion; structured valid seeds. Reset all instance state per case and retain minimized regressions. [C-21] |
| Sanitizers | ASan+UBSan in one practical lane; targeted integer-conversion checks with documented modular-arithmetic exclusions. MSan on fully instrumented supported builds; TSan for actual concurrency seams. These tools find different bug classes. [C-19–C-23] |
| Consumer contracts | Clean offline source archive; `add_subdirectory`; installed `find_package`; relocated install; C and C++ header consumers; static/shared linking; pkg-config; no leaked private include paths or third-party symbols. |
| End-to-end | Small redistributable program through native harness and libretro adapter; fixed input/movie plus frame/audio/state evidence; host save export/ack/restore and clean shutdown. |

Use a fixed regression corpus in required CI and budgeted discovery fuzzing on scheduled jobs. libFuzzer remains useful and supported for fixes, but its authors no longer develop major features; keep target entry points portable to other engines. [C-21] Promote reproducible failures into fast gates, not ever-growing random PR runtimes. Measure test/build wall time, CPU utilization, flake rate, and cache correctness. Keep performance discovery and sanitizer runs separate from release-speed measurements.

Validate diagnostic infrastructure itself. Playstead found a homebrew startup/linker defect hidden by a program using only constant globals; initialized writable data and zeroed BSS need their own assertions. An emulator-only fixture is not automatically valid hardware evidence. See [PROJECT-DNA.md](PROJECT-DNA.md), DNA-03. Each public-contract change should update headers, examples, lifecycle documentation, and relevant compatibility/version notes in the same PR; build the examples as consumers so documentation drift becomes detectable.

## First decisions to validate

Before implementation plans harden: prove backend instance isolation and state completeness; agree observable timing precision; choose the first output/ownership contract with a tiny host; validate one offline installed-package consumer; audit every imported file and fixture. These are bounded evidence tasks, not reasons to prebuild every future subsystem. Revisit this document when a dependency, supported platform, public contract, or hardware finding changes.
