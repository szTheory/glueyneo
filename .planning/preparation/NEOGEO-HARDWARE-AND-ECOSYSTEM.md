# Neo Geo hardware, ecosystem, and compatibility preparation

Status: research and proposed decisions, not an implemented emulator or compatibility claim. Accessed: **2026-10-01**. Scope: a portable C core for Neo Geo MVS/AES, reusable by Playstead and other hosts. No commercial ROM or BIOS was downloaded. Source IDs `HW-*` identify evidence in the ledger below; recommendations are engineering synthesis unless attributed otherwise. Mutable upstream pages must be pinned again before implementation.

## Recommended direction

Build an original board model, scheduler, renderer, cartridge layer, and public C API around carefully audited CPU/audio components. Spend original research effort on measurable gaps: event timing, cartridge behavior, reproducible state, diagnostics, portability, and integration. Reimplementing every CPU opcode and FM detail immediately would consume the compatibility budget before users can play anything. Forking a complete existing emulator would inherit its architecture and obscure the project's distinct purpose.

The target is a trustworthy and fast emulator with explicit evidence, including known limitations. “All games boot,” “matches MAME,” “looks correct,” and “cycle accurate” are different claims. Geolith itself combines a commercial-library compatibility claim with an explicit instruction-level CPU and best-effort video caveat. That is a useful distinction to preserve. [HW-15](https://raw.githubusercontent.com/libretro/geolith-libretro/master/README)

Ship small playable releases through a thin libretro adapter and RetroArch on macOS while retaining an independent native C API. Keep early work focused on cartridge MVS/AES. CD/CDZ, dedicated PCBs, unusual controllers, and multi-slot machines belong in the coverage inventory from the beginning, then enter implementation through explicit later slices.

## Hardware facts that shape the design

| Area | Evidence and implementation consequence |
|---|---|
| Clock domains | MVS uses a nominal 24 MHz master clock: 68000 at 12 MHz, Z80 at 4 MHz, YM2610 at 8 MHz, pixels at 6 MHz. Nominal NTSC timing is 384 pixels × 264 lines, yielding about **59.1856 Hz**, not 60. Use integer emulated time and rational reported rates. AES oscillator/PAL values need board-specific corroboration; the wiki framerate page explicitly requests scope measurements. [HW-04](https://wiki.neogeodev.org/index.php/Clock), [HW-05](https://wiki.neogeodev.org/index.php/Display_timing), [HW-06](https://wiki.neogeodev.org/index.php/Framerate) |
| 68000 bus | Model the 24-bit address space, byte lanes, big-endian values, mirrored RAM/registers, BIOS/cartridge vector switching, bank windows, and access waitstates explicitly. The map has 64 KiB work RAM, fixed/banked program regions, palette RAM, memory card space, BIOS, and MVS backup RAM. CPU instruction correctness alone cannot validate these connections. [HW-01](https://www.nxp.com/docs/en/reference-manual/MC68000UM.pdf), [HW-07](https://wiki.neogeodev.org/index.php/68k_memory_map) |
| Sound CPU | The Z80 has its own memory and four bank windows; communication uses byte latches and an enabled NMI, with replies separate from commands. YM2610 timers generate its IRQ. Schedule communication and bank changes at emulated times; do not substitute a frame-end “play sound” callback. [HW-08](https://wiki.neogeodev.org/index.php/Z80), [HW-09](https://wiki.neogeodev.org/index.php/68k/Z80_communication), [HW-10](https://wiki.neogeodev.org/index.php/Z80_bankswitching) |
| Audio chip | YM2610 provides four FM, three SSG, six ADPCM-A, and one ADPCM-B channels. SSG analog output is mixed externally with the DAC output. Digital synthesis, board mixing/filter response, host resampling, and device underruns need separate evidence. A YM2610B or YM2612 substitute is not equivalent. [HW-11](https://wiki.neogeodev.org/index.php/YM2610) |
| Video | Sprites are vertical strips of 16×16 tiles with chaining, wrapping, shrinking, palette attributes, and automatic animation; FIX is a separate layer. Hardware limits and sprite priority must survive optimization. The research wiki describes 96 active sprites per line and double-buffered scanline rendering, but explicitly marks its detailed sprite-parsing chronology as a draft. Preserve that uncertainty in tests and comments. [HW-12](https://wiki.neogeodev.org/index.php/Sprites), [HW-13](https://wiki.neogeodev.org/index.php/Rendering_logic) |
| Raster IRQ | The programmable display counter advances with pixels and has reload/acknowledgment behavior; it is not simply a scanline interrupt. Neo Turf Masters is a documented example of frequent raster updates. Test boundary writes, counter reload, simultaneous events, acknowledgment, and power-on versus reset. [HW-14](https://wiki.neogeodev.org/index.php/Timer_interrupt) |
| Persistent devices | BIOS identity, region, machine mode, backup RAM, memory card, and RTC are separate state. MVS RTC has an independent 32.768 kHz source. Host time must enter through an explicit initialization policy and thereafter advance deterministically. Save a machine profile with replays and states. [HW-07](https://wiki.neogeodev.org/index.php/68k_memory_map), [HW-16](https://wiki.neogeodev.org/index.php/Memory_card), [HW-17](https://wiki.neogeodev.org/index.php/RTC) |
| Cartridges | P/C/S/M/V regions have different roles; later boards add CMC graphics/audio decryption, SMA banking/PRNG, PVC, PCM2, and game-specific protection. Decryption of an image does not necessarily remove live protection. Separate immutable image preparation from mutable cartridge devices. [HW-18](https://raw.githubusercontent.com/mamedev/mame/master/src/mame/snk/neogeo.cpp), [HW-15](https://raw.githubusercontent.com/libretro/geolith-libretro/master/README) |

Manufacturer CPU manuals are the first authority for documented behavior. The scanned SNK development manual is an archival primary source, not a redistribution grant; link to it instead of copying it into the repository. Hardware measurements can supersede incomplete documentation when the board revision, experiment, and capture are reproducible. Community research and emulator source are invaluable but can share the same untested assumption. [HW-01](https://www.nxp.com/docs/en/reference-manual/MC68000UM.pdf), [HW-02](https://www.zilog.com/docs/z80/um0080.pdf), [HW-03](https://www.neogeodev.org/NG.pdf)

## Decision register

These are defaults for project initialization. “Revisit” means new evidence or an unmet acceptance criterion, not recurring debate each milestone.

| Decision / accountable lenses | Recommendation and alternatives | Cost, failure mode, revisit trigger |
|---|---|---|
| Machine scope — product, preservation, QA | Establish one documented MVS board profile first; add AES mode/BIOS behavior early. Inventory PAL, multi-slot, CD/CDZ, dedicated PCBs, and peripherals separately. Starting with everything exposes more code before any end-to-end evidence exists. | Initial coverage is narrow. Expand when the preceding slice has deterministic fixtures, documented gaps, and an installable release. Never infer AES/PAL correctness from MVS playback. |
| Scheduling — CPU, embedded, performance | Use deterministic integer deadlines, explicit tie ordering, and a time unit capable of half-master-clock positions if measured behavior requires them. Begin with a small fixed set of device deadlines. A general event framework is unnecessary initially; host wall time must stay outside. | Instruction-based CPUs can cross an event internally. Document this limitation and add timestamped bus/cycle detail when a hardware test exposes it. Half-clock representability alone proves no timing fidelity. HW-13 describes fractional master-clock access slots. |
| Renderer — graphics, portability, education | Start with a readable scalar scanline renderer preserving observable writes and hardware sprite rules. Optimize immutable tile decoding, locality, and common cases under differential tests. GPU rendering is a later optional host/presentation concern. | Whole-frame rendering misses raster writes; rendering every pixel/device clock immediately is expensive. Add finer segmentation where evidence requires it; SIMD only after measured gains on supported architectures. |
| Audio — DSP, determinism, UX | Clock synthesis and timers from emulated time. Expose a documented sample stream/rate and preserve fractional sample phase. Keep host buffering and rate adaptation in adapters; retain synthesis and resampler state where needed for replay. | A fixed integer sample count per video frame drifts. Silence must not disable timers or Z80 execution. Revisit mixing/filter models using measured audio, not subjective “sounds nicer.” |
| Content loading — security, DX, archivists | Native core accepts validated region descriptors and board identity. A reusable importer handles archive/manifest formats and emits actionable missing-region, wrong-size, wrong-BIOS, and unsupported-board errors. Start fixtures with explicit regions; add common MAME-style ZIP layouts before broad adoption, then `.neo` import if useful. | `.neo` alone simplifies loading but adds a conversion barrier; filename-only matching rejects renamed content; guesswork can select the wrong board. Hash-based identification plus explicit manifests handles ambiguity. Bound decompression, counts, sizes, offsets, and aggregate memory. |
| Profiles — players, preservation, maintainers | Faithful hardware behavior is the default. Crop metadata, control remapping, shaders, and accessibility belong to hosts. Overclock, slowdown removal, patches, and other enhancements must be explicit capabilities included in replay identity. | Quietly changing gameplay breaks reference comparisons. Preserve 320-pixel output with a recommended visible crop; do not erase hardware edge artifacts in the renderer. Revisit defaults through measured usability and compatibility evidence. |
| Persistence — library integrators, reliability | Distinguish cold boot, reset, state restore, backup RAM, and removable cards. Serialize explicit fields and pending events; validate identity/version before mutation. Host persists exported blobs atomically. | Dumping C structs embeds padding/pointers and backend details. Reject incompatible states clearly; support documented migrations only when justified. Revisit if upgrades strand users' permanent saves. |
| Debugging — homebrew, support, security | Offer disabled-by-default counters and bounded event traces for bus access, IRQ, banks, sound, and state operations. Let hosts supply sinks. Record build/profile IDs and test seeds; sanitize paths and content-derived output. | Always-on per-instruction logging destroys throughput and may expose private content. Compile expensive traces out of release builds; measure enabled/disabled overhead. Debugger sockets, if added, are optional host features. |
| First GUI — adoption, macOS, release engineering | Publish a libretro adapter, metadata, and instructions for RetroArch's macOS build. Exercise native API behavior in a headless reference host. SDL3 is a sensible optional simple host if it pays for itself in integration diagnostics. | RetroArch brings configuration complexity; writing a native GUI creates a second product. OpenEmu/custom integrations can follow demand. Revisit if loading the distributed core cannot be made reliable in a documented supported host. [HW-32](https://www.retroarch.com/platforms.php), [HW-33](https://docs.libretro.com/development/cores/developing-cores/), [HW-34](https://www.libsdl.org/) |

Libretro is an adapter contract, not the native architecture: its documented implementation model is single-instance and gives no general reentrancy guarantee. Glueyneo's instance ownership, lifetime, error handling, and test seams should remain independent. Package the `.info` file and verify actual load/unload flows: a real RetroArch report demonstrates that a core can partly load while missing metadata breaks associated-content handling. [HW-33](https://docs.libretro.com/development/cores/developing-cores/), [HW-35](https://github.com/libretro/RetroArch/issues/15553)

## Reuse and licensing: conditional selections

No candidate below is approved for vendoring by this research. Before adoption, record the exact revision, all compiled/generated files, license notices, transitive dependencies, local changes, update policy, and test evidence. A repository badge or permissively licensed header does not establish the provenance of every compiled file or bundled asset.

| Component | Preferred route, alternatives, tradeoff, acceptance trigger |
|---|---|
| Board core | Original C modules using documented hardware behavior. An audited Geolith fork could reach playback sooner but would make Glueyneo a derivative architecture project. Choose original composition for an educational, reusable core; revisit only if maintaining independent board behavior produces no measurable user benefit. |
| 68000 | **Musashi is the first feasibility candidate**, with MIT-style grants in its source and portable C implementation. It already handles substantial CPU complexity. Its mutable globals include CPU, cycle, exception, and jump-buffer state; context copying alone does not make independent concurrent instances safe. Require contextization or a clearly restricted prototype, opcode/exception tests, interrupt/bus timing characterization, and repeatable generation. An original interpreter improves ownership but delays compatibility; assembly/JIT backends add platform and verification cost. [HW-19](https://github.com/kstenerud/Musashi), [HW-20](https://raw.githubusercontent.com/kstenerud/Musashi/master/m68kcpu.c) |
| Z80 | Evaluate **Jolly Good Z80** from Geolith first for a small C implementation already integrated with Neo Geo; its license file is MIT. Compare **chips/z80.h**, a zlib-licensed cycle-stepped C implementation with explicit instance state, if event granularity or reentrancy needs are easier there. Choose one production backend after NMIs, IRQs, banking, undocumented behavior, state restoration, and cost are measured. Do not retain two by default. [HW-21](https://raw.githubusercontent.com/libretro/geolith-libretro/194024931935eff2092e36fc4f8e53e62ed11097/src/z80/LICENSE), [HW-22](https://raw.githubusercontent.com/floooh/chips/master/chips/z80.h) |
| YM2610 | **YMFM-C from Geolith is the pure-C feasibility candidate**, with BSD-3-Clause headers. It contains mutable static synthesis/timer/output state, global callbacks, and `geo_serial.h` coupling. Budget contextization, serialization isolation, and comparison with upstream fixes before accepting it. Upstream **ymfm** is BSD but C++14; a C ABI wrapper is technically attractive yet changes the all-C requirement, so it is an explicit fallback decision. A fresh FM implementation has the largest accuracy/research cost. Neither candidate promises complete digital pipeline accuracy. [HW-23](https://raw.githubusercontent.com/libretro/geolith-libretro/master/src/ymfm/ymfm_opn.c), [HW-24](https://raw.githubusercontent.com/libretro/geolith-libretro/194024931935eff2092e36fc4f8e53e62ed11097/src/ymfm/ymfm_shim.c), [HW-25](https://raw.githubusercontent.com/aaronsgiles/ymfm/main/README.md) |
| MAME | Use as a reference and differential runner. The complete modern project is GPL-2.0-or-later; some files, including the inspected Neo Geo driver, have BSD-3-Clause headers. Any extraction needs a per-file and dependency audit at a pin. A modern license must not be projected onto older MAME code. [HW-18](https://raw.githubusercontent.com/mamedev/mame/master/src/mame/snk/neogeo.cpp), [HW-26](https://www.mamedev.org/legal.html) |
| FBNeo / GnGeo / old MAME | Learn behavior, diagnostics, and regression lessons; do not copy restricted code into a permissive core. FBNeo's license includes noncommercial and source-sharing restrictions. GnGeo's README describes GPLv2 with an exception plus components imposing further restrictions. Historical MAME variants have separate licensing. This is a dependency selection constraint, not a judgment on emulator quality. [HW-27](https://github.com/finalburnneo/FBNeo/blob/master/src/license.txt), [HW-28](https://raw.githubusercontent.com/pepone42/gngeo/master/README), [HW-29](https://github.com/libretro/docs/blob/master/docs/development/licenses.md) |

Inspected candidate snapshots: Musashi `313ebf1bd9f4d0d93341eb5ce21fd8a119e9dbdd`; Geolith libretro `194024931935eff2092e36fc4f8e53e62ed11097`; upstream ymfm `81aec25ccbb98f4873a255f7551ac4dadac59b4a`; chips `9e88298ce56319953ac7a43213a1120359f7a3a6`. These identify the examined revisions, not endorsements of their latest status or completeness. The first milestone should settle these dependencies with bounded experiments before extending gameplay coverage.

## Lessons from existing emulators and actual reports

This is a targeted qualitative sample, not a popularity survey or a current defect ranking. Historical closed issues are regression design inputs. Upstream claims remain claims until independently tested.

| Evidence | Lesson and proposed response |
|---|---|
| Current MAME Neo Geo driver lists raster discrepancies, ROM waitstates, AES clock, and PAL verification gaps. It also documents edge artifacts and sound/graphics oddities as hardware behavior. [HW-18](https://raw.githubusercontent.com/mamedev/mame/master/src/mame/snk/neogeo.cpp) | Maintain a hardware-evidence backlog and “known hardware behavior” catalog. Agreement with a mature emulator is useful but incomplete. Do not improve appearance by silently changing the machine. |
| MAME reports describe switching games producing crashes/reset loops; another reports BIOS choice being lost on subsequent GUI launches. [HW-36](https://github.com/mamedev/mame/issues/4520), [HW-37](https://github.com/mamedev/mame/issues/4531), [HW-38](https://github.com/mamedev/mame/issues/12622) | Automate A→B→A load sequences, failed-load recovery, repeated initialization, BIOS/profile retention, and teardown. A fresh-process boot test misses integration state leaks. |
| FBNeo's official FAQ discusses mismatched sets, missing BIOS/black screens, choppy audio, CPU-backend state incompatibility, and latency features. It documents rewind, netplay, achievements, and runahead support. [HW-30](https://docs.libretro.com/library/fbneo/) | Preserve the valued interaction features through deterministic state and good adapters. Give structured content errors and a preflight command. Benchmark with sound and realistic latency settings; state clearly which backend/profile a save needs. |
| Geolith documents `.neo`-only cartridge loading and precise scope caveats. Its tracker contains requests for per-content DIP storage, high scores, and achievements; its NONBUGS file distinguishes original defects. [HW-15](https://raw.githubusercontent.com/libretro/geolith-libretro/master/README), [HW-31](https://github.com/libretro/geolith-libretro/issues), [HW-39](https://raw.githubusercontent.com/libretro/geolith-libretro/master/NONBUGS) | Simple content packaging and focused scope aid adoption; conversion and persistence gaps create friction. Publish a coverage matrix, preserve per-content machine configuration in the host, and expose safe memory inspection when achievement integration is justified. |
| GnGeo exposes alternative CPU implementations, overclock/frameskip/raster settings, and benchmarking. Its own README marks PAL timing as problematic. [HW-28](https://raw.githubusercontent.com/pepone42/gngeo/master/README) | Performance shortcuts need named profiles and cross-backend regression evidence. Average FPS alone hides hitches and audio failure. Preserve one clear default behavior. |
| ares explicitly discusses a clarity/speed tradeoff in its multi-system architecture, with cores, UI, platform I/O, and image loading separated. [HW-40](https://raw.githubusercontent.com/ares-emulator/ares/master/README.md) | Readable chip models and strong host boundaries are valuable. Copying its coroutine/bitfield design is unnecessary for a small C board. Compare scheduler approaches on clarity, profiling results, and portability; ares is a cross-system lesson here, not proof about MVS/AES compatibility. |

For every reproduced report, retain a minimal lawful fixture, exact machine profile, input sequence, expected observation, and the fix's evidence. Avoid enormous goldens that only say “different.” A failing test should identify the first diverging bus event, register, scanline, or audio interval when feasible.

## Defining eventual “all games” coverage

Define the inventory as commercial MVS/AES **titles and revisions**, linked to cartridge families and supported BIOS/machine profiles. Maintain separate categories for prototypes, hacks, bootlegs, post-commercial homebrew, multi-slot operation, dedicated PCBs, and CD/CDZ. A raw count without its denominator is misleading.

| Coverage dimension | Representative evidence to collect |
|---|---|
| Basic board | Cold boot, attract, coin/start, both players, resets, watchdog, BIOS services, ordinary bank switching. |
| Raster/video | FIX banking, sprite overflow/chaining/shrink/wrap, palette timing, animation, 304/320 presentation, IRQ boundary cases; Neo Turf Masters provides a documented raster scenario. HW-12–14. |
| Audio | Command bursts, Z80 bank windows/NMI, timer IRQ, FM envelopes, SSG noise, ADPCM boundaries/end flags, simultaneous playback, long-duration drift. |
| Protected carts | CMC42/50, SMA PRNG/banking, PVC, PCM2, and separate special protection families. Select representatives from an audited driver inventory rather than assuming each title uses identical hardware across revisions. [HW-41](https://wiki.neogeodev.org/index.php/NEO-SMA), [HW-42](https://wiki.neogeodev.org/index.php/NEO-CMC), [HW-43](https://wiki.neogeodev.org/index.php/NEO-PVC), [HW-44](https://wiki.neogeodev.org/index.php/NEO-PCM2) |
| Persistence/input | Backup RAM restored after process restart, insert/remove/write-protect card, deterministic RTC, DIP retention, trackball, mahjong, four-player extension where supported. |
| Integration | Multiple independent instances; native and libretro equivalent outputs; unload/load/error recovery; state roundtrip; rewind/runahead without persistent side effects; cross-platform replay. |

Use evidence states such as **unexamined**, **identified**, **boots**, **scripted scenario passes**, **extended gameplay observed**, **hardware compared**, and **known discrepancy**. Every entry includes source/pin, machine/BIOS identity, sequence, duration, capture method, test version, and known gaps. Automatic attract-mode and gameplay replays scale coverage; neither proves every game path. Rare endings, protection checks, region branches, and persistence interactions need targeted scenarios.

Private owner-supplied ROM testing can expand coverage without publishing bytes, saves, screenshots, private hashes, paths, or credentials. Public CI must remain independently useful. A missing private corpus must produce a visible “not evaluated” result, never a green compatibility claim.

## First demonstrable slices and acceptance

1. **Dependency and evidence foundation:** a packaged C library, importer contract, chip acceptance experiments, headless runner, self-authored boot fixture, and baseline metadata. Acceptance includes malformed-input handling and repeatable builds; no game compatibility claim.
2. **Visible, interactive, audible board:** fixture drives FIX/sprites, palettes, both players, Z80 commands, representative YM2610 channels, timer IRQs, and bank changes. Native/libretro outputs agree for identical input; ship a macOS core artifact and a short RetroArch guide.
3. **First real cartridge profile:** owner-supplied unprotected games, documented BIOS mode, end-to-end loading/persistence, scripted replay, save/restore continuation, honest limitations. Public equivalents exercise every fixed mechanism.
4. **Coverage by mechanism:** expand protection/video/input families using minimal regressions and representative titles, then broaden title/revision inventory. Optimize demonstrated hot paths while retaining earlier correctness gates. Add hardware experiments where reference implementations disagree.

Record emulated seconds per host second, work per frame, allocations, resident/peak memory, startup/import time, state size/latency, audio underruns at the host boundary, and CI cost. Compare equal profiles and enabled features. Original hardware slowdown remains emulated behavior. Tail frame times require sufficient sample counts and controlled machines; a short shared-runner job cannot substantiate a 99.999th-percentile claim. PRs should run compact deterministic correctness gates; longer corpus and controlled performance runs belong in scheduled/release lanes. Each optimization needs an observable speed/cost benefit and unchanged relevant evidence.
