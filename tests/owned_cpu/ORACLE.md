# Owned CPU timing and exception oracle

## Exception-entry baseline correction — 2026-10-12

This section is the current contract for exception-entry clocks and supersedes
the 2026-10-09 section below. It is an intentional baseline change under
AGENTS.md, taken from a primary source, not a relaxed expectation.

The selected processor is the 16-bit-bus MC68000. The controlling table is
Motorola/NXP M68000 User's Manual Rev. 9.1 Section 8, Table 8-14 "Exception
Processing Execution Times" (printed p. 8-11,
[official PDF](https://www.nxp.com/docs/en/reference-manual/MC68000UM.pdf)):
RESET 40(6/0), interrupt 44(5/3) with the interrupt-acknowledge cycle assumed
to take 4 clocks, address error and bus error 50(4/7), and illegal
instruction, privilege violation, trace and TRAP 34(4/3). Section 7 / Table
7-15 (printed p. 7-11: 64, 72, 94, 62) is the 8-bit-bus (MC68008) table and
was the wrong attribution in the 2026-10-09 section. The owned CPU models
clocks only; the read/write bus-cycle counts in parentheses are not core
counters and no exception-entry bus-count assertion exists.

Implemented constants (`experiments/owned_cpu/cpu.c`): `RESET_EVENT_CYCLES` 40,
`EXCEPTION_IRQ_CYCLES` 44, `EXCEPTION_ADDRESS_ERROR_CYCLES` 50 and
`EXCEPTION_INSTRUCTION_CYCLES` 34. The no-charge candidate rejection still
charges nothing. The stopped-CPU idle path, the reset-request split
(requests 39, 40 and 41) and counter-overflow preflight use the same constants.

Every changed expectation equals its old value minus the Table 8-14 versus
Table 7-15 delta of the event the scenario contains, applied once per event:

| Event | Table 7-15 (old) | Table 8-14 (new) | Delta per event |
|---|---:|---:|---:|
| reset recovery | 64 | 40 | -24 |
| autovector interrupt entry | 72 | 44 | -28 |
| address / bus error | 94 | 50 | -44 |
| illegal instruction, privilege violation, TRAP | 62 | 34 | -28 |

Diagnostic derivations: the 12-instruction run is 40 reset + 132 instruction
clocks = 172 (was 196); cumulative boundaries are 40, 44, 52, 72, 76, 92, 100,
120, 124, 140, 148, 168, 172; reset-only requests 1, 39, 40 and 41 report
elapsed 40, 40, 40 and 44; the cold-start total is 76 (was 100). Diagnostic
output digests and `fixtures/diagnostic/manifest.json` were regenerated only
after the freshly built runner reported the hand-derived 172 tuple. Values
that do not include one of the four events (instruction clocks, frame-clock
positions in the MVS board tests, and the arbitrary seeded total-cycle counter
64 in `independent_counter_boundaries_do_not_block_other_event_kinds`, whose
derived total 68 is unchanged) were not touched, and no budget, allowlist or
golden changed. No MVS board expectation includes an interrupt-entry clock
total; the only board-test changes are the 15 reset-only budget runs (40 instead of 64).

History: the test commits carrying only these expectations failed on the
previous implementation before the CPU constants changed (RED), then the
constant commits made the same expectations pass (GREEN); see the plan 05-18
rows in [retired Phase05 validation](../../.planning/milestones/ws-first-playable-game-2026-10-24/retired/2026-10-16-development-workflow/phase05/05-VALIDATION.md).

### Stack-bank regression record

`write_address_register()` keeps the banked pointer of the active mode equal
to A7 after every A-register write. The table-driven regression
`address_register_writes_keep_the_active_stack_bank_consistent` runs each
admitted A-register writer with A7 and with A3 as the written register, in
supervisor and user mode, and checks the active and inactive banks, then
restores the captured state into a fresh owner. JSR, BSR and RTS use the active
(user or supervisor) stack; exception frames run after SR.S is set and still
push on the supervisor stack.
